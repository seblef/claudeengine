# VFXScrape

Implements GitHub issue #830: `vfx::VFXScrape` — continuous directional sparks + a
looping metal screech while a vehicle panel scrapes geometry at speed.

## Summary of changes

### `physics/` — sustained-contact plumbing (new capability, didn't exist before)

The issue's scope line "Triggered by `VehicleDamage` when a panel is in sustained
contact with geometry at speed" assumes the game layer can already learn "this
panel is still touching that wall, here's the surface normal and sliding speed."
No such channel existed: `IPhysicsCollisionListener::OnCollision` only fires once
when a contact *begins* (added for issue #828's `VehicleDamage`), and
`VehicleContactListener::OnContactPersisted` was explicitly a no-op ("resting/
sliding contact should not repeatedly trigger damage" — correct for damage, but
scrape needs exactly this signal).

- **`IPhysicsCollisionListener.h`** — new `OnSustainedContact(world_point,
  world_normal, relative_velocity)`, fired every physics step a registered body
  remains in contact. `world_normal` is oriented toward the registered body (the
  listener always sees "the other surface's normal, pointing at me"), and
  `relative_velocity` is this body's velocity relative to the other body at the
  contact point (into-surface + sliding components, not just a scalar speed —
  the reflection math in `VFXScrape` needs the vector, not only its magnitude).
- **`PhysicsSystem.cpp`** — `VehicleContactListener::OnContactPersisted` now computes
  this from the manifold (`mWorldSpaceNormal`, sign-flipped per listener since Jolt
  defines it as "direction to move body 2 out of collision" — i.e. body 1's own
  outward normal, the opposite of what each listener wants) and
  `Body::GetPointVelocity()` for both bodies. Factored the contact-point averaging
  (shared with `OnContactAdded`) into a small `AverageContactPoint()` helper to
  avoid duplicating the manifold-iteration loop.
- Not visually/physically verified against a real collision (no display in this
  environment, same caveat as issue #828's contact-impulse plumbing) — the sign
  convention for `world_normal` is derived from Jolt's documented manifold
  semantics but flag for manual QA (grind the car along a wall, confirm sparks
  fly away from the wall, not into it).

### `physics/VehicleDesc.h` — new `ScrapeDesc`

`min_speed`/`max_speed` (sliding-speed range spark rate and screech gain are
normalised against), `base_emission_rate`, `base_gain`, `contact_grace_time`
(tolerates single-step contact gaps from solver jitter so the effect doesn't
flicker), `screech_sound` (asset stem, defaults to `scratching_metal` — the same
placeholder sound already used for all three `VehicleCrashSound` tiers).

### Architecture decision: `VehicleScrapeEffect` lives in `vfx/`, not `game/`

The issue phrased the trigger as "Triggered by `VehicleDamage`," but implementing
it literally inside `game::VehicleDamage` would conflate two unrelated
responsibilities: `VehicleDamage`'s own contract is to be "the single
authoritative source of vehicle damage state" (its existing doc comment) — a
scrape effect doesn't damage the panel, it's a cosmetic/audio effect layered on
raw contact data.

More importantly, a straightforward "own the effect in `game::GameVehicle`, like
`VehicleCrashSound`" design doesn't compile: driving `vfx::VFXScrape` requires
`vfx::VFXSystem::Spawn()`, but `vfx/ → game/` already (per `WRECKONING.md` §12 and
the #827 scaffold) — `game/` depending back on `vfx/` would be a circular library
dependency.

Resolution, mirroring the existing `IVehicleController`/`SetVehicleController()`
non-owning-pointer pattern already on `GameVehicle`:

- **`game/IVehicleScrapeListener.h`** (new, vfx-free) — `Update(dt)` +
  `RegisterContact(world_point, world_normal, relative_velocity)`.
- **`GameVehicle`** gains a non-owning `IVehicleScrapeListener* scrape_listener_`
  (default `nullptr`, set via `SetScrapeListener()`), ticked from `Update()`
  alongside `crash_sound_->Update(dt)`, and fed from the new
  `OnSustainedContact()` override (added to `IPhysicsCollisionListener`).
- **`vfx::VehicleScrapeEffect`** (new, implements `game::IVehicleScrapeListener`)
  is the concrete trigger: on the first contact at/above `min_speed` it
  `vfx::VFXSystem::Instance().Spawn()`s a `VFXScrape` and keeps the returned raw
  pointer; every subsequent `RegisterContact()` call feeds it
  `UpdateContact()`; `Update(dt)` advances a no-contact grace timer and calls
  `Stop()` once it lapses (or immediately if speed drops below `min_speed`).
  Since it owns the caller's decision to stop, it never touches the pointer
  again after nulling it — no risk of dereferencing an instance `VFXSystem`
  later reaps.
- **Wiring**: `src/app/main.cpp`'s standalone `--vehicle` spawn path constructs a
  `vfx::VehicleScrapeEffect` alongside `player_vehicle_ctrl` and calls
  `vehicle_ptr->SetScrapeListener(...)`, exactly mirroring how the immediately
  preceding crash-sound-audio branch threaded `sound_manager`/`resource_manager`
  into every `GameVehicle` construction site. `vehicle_scrape.reset()` is called
  explicitly right before `vfx::VFXSystem::Shutdown()` (rather than relying on
  its end-of-`main()` destruction) — otherwise its destructor would call
  `Stop()` on a raw pointer into a `VFXSystem` instance already deleted by
  `Shutdown()`, a real use-after-free on process exit while a scrape happened to
  be active.

### `vfx::VFXScrape` (new, per issue scope)

- Satisfies `IVFXEffect` (`Play`/`Update`/`IsFinished`) so `VFXSystem` still owns
  and reaps it normally, but — unlike every other effect — `Play()` only does
  minimal setup; the real per-frame work happens in the new `UpdateContact()`,
  called directly by `VehicleScrapeEffect` on the pointer `Spawn()` returned.
  `Stop()` ends the effect immediately and precisely (contact lost, or speed
  below threshold); `Update(dt)` itself only ticks the particle simulation and
  never decides when the effect ends.
- Owns a `particles::ParticleSubSystemDesc` **by value** (not a reference into a
  shared template) specifically so `direction` and `emission_rate` can be
  mutated every `UpdateContact()` call — `ParticleEmitter` stores its desc by
  reference, so as long as the referenced struct is a stable-address member
  declared before the emitter, live mutation works without reconstructing the
  emitter each frame. The struct is seeded once from a new `sparks.particles.yaml`
  template (authored constants: lifetime, size, color gradient, gravity, drag)
  and then only `direction`/`emission_rate` change per contact update.
  `renderer::Renderer::GetVideoDevice()` (new trivial getter, mirroring the
  `GameSystem::GetCameraController()`/`GetActiveCamera()` precedent from #827)
  supplies the `abstract::VideoDevice*` needed to construct the `ParticleEmitter`
  on demand — no prior code path did this outside map-load/editor-placement.
  Guarded by `Renderer::IsInstanced()` so unit tests (no `Renderer` constructed)
  exercise every other code path safely.
- `ReflectDirection(incoming, normal)` reflects the **full** relative-velocity
  vector (not just its tangential component) off the surface normal — this is
  what makes it look like "sparks bouncing off a surface" rather than just
  "sparks flying along the slide direction": the into-surface component flips
  outward, the tangential (sliding) component is preserved.
- `ComputeIntensity(speed, desc)` linearly normalises `[min_speed, max_speed] →
  [0, 1]`, used to scale both spark `emission_rate` and screech `gain`
  identically (issue acceptance criterion: "spark rate and screech intensity
  rise with speed").
- Screech uses `SoundManager::PlaySound(..., loop=true, ...)`, overriding the
  sound asset's own `loop: false` field — the same "explicit loop override"
  already established by `GameSoundEmitter`.

### `data/particles/sparks.particles.yaml` (new)

No dedicated spark sprite exists in the repo and none was fabricated for this
issue; a pre-commit hook flagged the initially-textureless sub-system, so it
now points at the existing `default/diffuse.dds` placeholder (a flat white
quad) rather than a real spark shape. Bright yellow-white → orange →
transparent-red 3-stop gradient, `intensity_start: 3` for bloom, short lifetime
(0.15–0.4s), moderate gravity and drag so they arc and decelerate quickly. Flag
for a follow-up with an artist-made spark sprite/atlas.

### Known limitation: no effect in the editor's Play Mode yet

`vfx::VFXSystem` is only instantiated and ticked by `src/app/main.cpp` (the
standalone `wreckoning` app) — `EditorSystem`/`PlayModeManager` never create or
tick it, and `editor/CMakeLists.txt` doesn't even link `vfx`. This means
`VFXScrape` (and the already-merged `ScreenShake` before it) silently do nothing
when Play-testing a vehicle inside `wreckoning_editor`, even though
`VehicleScrapeEffect::RegisterContact()` guards safely on `VFXSystem::
IsInstanced()` rather than crashing. This is a pre-existing gap from the #827
VFX scaffold, not introduced by this issue, and out of scope to fix here (it's
a `PlayModeManager`/`EditorSystem` wiring change, not specific to scrape) — but
worth flagging clearly since it means Play Mode QA cannot currently confirm any
VFX effect end-to-end.

### YAML round-trip (`.vehicle.yaml`) and editor UI

Added `scrape:` to both parse paths (`VehicleTemplate.cpp`, mirroring
`ParseDamageDesc`/`ParseCrashSoundDesc`) and a `DrawScrapeSection()` in
`VehicleEditorWindow.cpp` (sound picker + 4 drag floats), inserted between the
existing Crash Sound section and the actions bar. Added `scrape:` to
`hell_sized.vehicle.yaml` only (matching `damage`/`crash_sound`, which are also
only tuned there — `hell.vehicle.yaml` and `test_box.vehicle.yaml` rely on
`ScrapeDesc`'s in-code defaults).

### Tests

- `tests/vfx/VFXScrapeTest.cpp` — `ComputeIntensity` (below/at/above thresholds,

  no-op, normalisation, zero-length fallback), and `Play`/`Stop`/`IsFinished`

  survive the grace timer, long gaps stop it, a refreshed contact resets the
  timer, dropping below `min_speed` stops immediately, plus one un-fixtured test
  confirming `RegisterContact()` is a safe no-op with no `VFXSystem` instanced.
- Switched `tests/vfx/CMakeLists.txt` from recompiling `VFXSystem.cpp` inline
  (its previous zero-dependency shortcut) to linking the real `game renderer
  particles audio physics` libraries `VFXScrape`/`VehicleScrapeEffect` need —
  `VFXSystemTest.cpp`'s existing tests are unaffected.

## Output to keep in mind for next Milestone 3 issues

- `physics::IPhysicsCollisionListener::OnSustainedContact` is now available for
  any future continuous-contact effect (e.g. a future tire-smoke-while-drifting
  system) — no further physics plumbing needed, just implement the interface.
- The `game/I...Listener.h` + non-owning-setter pattern (`SetScrapeListener`,
  mirroring `SetVehicleController`) is the template to follow whenever a `vfx/`
  (or any module above `game/`) effect needs to react to a `GameVehicle`
  callback — do **not** give `game/` a direct `#include "vfx/..."` dependency;
  it will not compile (circular library link).
- `sparks.particles.yaml` has no texture (flat additive quads) — replace with a
  real sprite once art is available; no code changes needed, just re-author the
  YAML.
- The editor Play Mode / `vfx::VFXSystem` wiring gap (see above) blocks visual
  QA for both `ScreenShake` and `VFXScrape` today — worth its own follow-up issue
  (`editor` needs to link `vfx`, `EditorSystem` needs to instantiate and tick
  `VFXSystem`, `PlayModeManager::Enter`/`Exit` need to construct/destroy a
  `VehicleScrapeEffect` the same way `main.cpp` now does).

## Propositions

**CLAUDE.md improvements** (not applied, proposing only):
- `src/vfx/CLAUDE.md` doesn't exist yet — worth creating one now that `vfx/` has
  4 source files; should document the `IVFXEffect` contract, the "continuous
  effect fed by an external `UpdateContact()`-style method beyond the base
  interface" pattern (`ScreenShake` vs. `VFXScrape` are genuinely different
  shapes), and the `game/I...Listener.h` + non-owning-setter wiring pattern for
  triggering `vfx/` effects from `game/` callbacks without a circular dependency.
- `src/physics/CLAUDE.md`'s module table doesn't mention `IPhysicsCollisionListener`
  or `OnSustainedContact` — same gap already flagged in the #828 history doc,
  now doubly relevant with a second consumer.
- `src/game/CLAUDE.md`'s module table doesn't list `IVehicleScrapeListener`.

**README.md**: no build/install process changes (no new third-party library) —
no proposal needed.

**Specification questions**: none blocking, but one significant judgment call
worth flagging explicitly: I deviated from the issue's literal "Triggered by
`VehicleDamage`" wording, routing sustained-contact events through a new
sibling interface on `GameVehicle` instead of through `VehicleDamage`, because
(a) `VehicleDamage`'s stated contract is specifically damage-state authority,
and (b) the actual blocking constraint is architectural: `vfx/` cannot be
depended on by `game/` in either direction without creating a circular library
link. I also scoped down by not wiring `PlayModeManager`/`EditorSystem` to tick
`vfx::VFXSystem` — see "Known limitation" above — since that gap pre-dates this
issue and affects `ScreenShake` too, not just `VFXScrape`.
