# VFXExplosion

Implements GitHub issue #831: `vfx::VFXExplosion` — the signature composited
effect (fireball/smoke burst + point-light flash + physics shockwave + screen
shake), proving the `VFXSystem` composition model end-to-end.

## Summary of changes

### `physics::PhysicsSystem::SphereOverlap` (new capability, didn't exist before)

The issue's scope line "Physics shockwave: `PhysicsSystem::SphereOverlap` in a
radius → outward impulse" assumes this query already exists. It didn't —
`PhysicsSystem` only exposed `Raycast()`. Added:

```cpp
[[nodiscard]] std::vector<PhysicsBody*> SphereOverlap(
    const core::Vec3f& center, float radius, uint16_t layer_mask = 0xFFFF) const;
```

Implemented as an exact narrow-phase query (`JPH::SphereShape` +
`NarrowPhaseQuery::CollideShape` + `JPH::AllHitCollisionCollector
<JPH::CollideShapeCollector>`), not a broad-phase-only `CollideSphere` (which
only tests AABB overlap and would produce false positives at the shockwave
edge). Reuses the existing anonymous-namespace `RaycastBroadPhaseFilter`/
`RaycastObjectLayerFilter` (they're generic layer-mask filters, not
raycast-specific despite the name) and resolves `JPH::BodyID` → engine
`PhysicsBody*` via the same linear scan `Raycast()` already uses. New Jolt
includes: `<Jolt/Physics/Collision/CollideShape.h>`,
`<Jolt/Physics/Collision/CollisionCollectorImpl.h>` — both confined to
`PhysicsSystem.cpp`, consistent with `physics/CLAUDE.md`'s "Jolt types must
not appear in any `physics/*.h`" rule.

No unit test added for `SphereOverlap` (or `Raycast`, which also has none) —
exercising it needs a live `JPH::PhysicsSystem` world, and there's no
`tests/physics/` directory or precedent for that kind of test in this repo
yet. Flagging as a gap, not fixing it here (out of scope for this issue).

### `vfx::VFXExplosionDesc` (new, header-only POD)

Tunable parameters, all with defaults so `VFXExplosionDesc{}` works as-is:
`particle_duration` (bounds `IsFinished()`, independent of the particle
sub-systems' own authored duration/lifetime), `light_color`/`light_intensity`/
`light_radius`/`light_lifetime`, `shockwave_radius`/`shockwave_impulse`,
`shake_base_magnitude`/`shake_duration`.

**Scope decision**: the issue doesn't request YAML (de)serialization for this
struct, and the milestone's "VFX panel for editing effect parameters" item is
explicitly a separate, later milestone step (this issue's own "Gates" line:
"VFXPanel (needs a concrete effect to edit)"). `WRECKONING.md` line 27 does
list `VFXExplosionDesc` among examples of "resource descriptors [that] are
YAML files," but adding a YAML loader with no consumer yet would be
speculative — left as a natural follow-up once the VFX panel issue lands
(mirrors how `physics::ScrapeDesc` only gained YAML round-trip when the
vehicle editor actually needed to edit it).

### `vfx::VFXExplosion` (new, per issue scope)

Composes four independent pieces inside one `IVFXEffect`:

1. **Particle burst** — unlike `VFXScrape` (which only ever uses sub-system
   index 0), `VFXExplosion::Play()` copies **every** sub-system out of
   `explosion_template_->GetSubSystems()` into a member `sub_descs_` vector,
   then constructs one `ParticleEmitter`/`ParticleRenderable` pair per
   sub-system — needed because a fireball is authored as two layered
   sub-systems (fire + smoke), not one. `sub_descs_` is populated once and
   never resized afterwards, so each `ParticleEmitter`'s stored `const
   ParticleSubSystemDesc&` reference (see `ParticleEmitter.h`) stays valid for
   the object's lifetime — same technique `VFXScrape` uses for its single
   `spark_desc_`, just generalised to a vector.
   - `explosion_template_` is a non-owning constructor parameter (may be
     `nullptr`), following the exact same rationale as `VFXScrape`'s
     `spark_template`: the caller must load it once (e.g. via
     `ParticleSystemTemplate::GetOrLoad(VFXExplosion::kExplosionTemplateName,
     video)`) and hold it for as long as explosions might trigger, so
     `core::Resource`'s "delete on ref-count zero" behaviour doesn't force a
     disk reparse on every single explosion. No owner class exists yet for
     this (unlike `VehicleScrapeEffect` for scrape) since the trigger
     (wreck state) is explicitly out of scope / a future issue — flagged
     below.
2. **Point-light flash** — a real `game::GameLight` (not a bare
   `renderer::OmniLight`), per the issue's literal wording ("spawn a
   `GameLight`"). Constructed with `cast_shadow = false` (a ~0.15s flash isn't
   worth a shadow map), registered via `game::GameSystem::Instance().
   AddObject()`/`RemoveObject()` — the `GameObject` scene-lifecycle API, not
   a direct `Renderer::AddRenderable()` call, since `GameLight::
   OnAddedToScene()`/`OnRemovedFromScene()` already own that registration.
   `Update(dt)` counts `light_elapsed_` and releases the light (removes +
   `reset()`s the `unique_ptr`) once `desc_.light_lifetime` is reached,
   independently of the rest of the effect's lifetime. The destructor also
   removes it early if the whole effect is torn down first.
3. **Shockwave** — fired once from `Play()` (not per-frame: a real explosion
   pushes things once, at the moment it detonates). Queries
   `PhysicsSystem::SphereOverlap(world_pos, shockwave_radius)`, skips any
   non-`Dynamic` body (`ApplyImpulse` asserts on Static/Kinematic in debug
   builds), computes outward direction from body position minus explosion
   center (falls back to `Vec3f::kAxisY` if a body sits exactly at the
   center, avoiding a zero-length normalize), and scales the impulse by a
   linear falloff (`1 - distance/radius`, clamped to `[0,1]`).
4. **Screen shake** — delegated entirely to the existing `vfx::ScreenShake`
   rather than reimplemented: `Play()` constructs one, sets
   `base_magnitude`/`duration` from `desc_`, and `VFXSystem::Instance().
   Spawn()`s it as an independent sibling effect (guarded by `VFXSystem::
   IsInstanced()`). `ScreenShake::Play()` already computes the "falls off
   with inverse distance from camera" math the issue asks for — no need to
   duplicate it. Consequence: the shake effect's lifetime is decoupled from
   `VFXExplosion`'s own — it keeps running (and gets reaped by `VFXSystem`)
   even after the explosion itself has self-expired. The issue's acceptance
   criterion only requires the *light* to be released on self-expiry, so
   this is within scope.

`IsFinished()` is a simple elapsed-time flag (`elapsed_ >=
desc_.particle_duration`), the same shape as `ScreenShake`'s — not wired to
any single sub-component's own completion state, since `ParticleEmitter`
doesn't expose a public "done" query (its private `done_` flag is
implementation detail) and the light/shockwave/shake all have independent,
shorter lifetimes than the fireball is expected to take to fade out.

### `data/particles/explosion.particles.yaml` (new)

Two sub-systems, both non-looping (`looping: false`) one-shot bursts:
`fireball` (additive, `fx/fireflamepart01anim.dds` — the same sprite sheet
`bonfire.particles.yaml` already uses, 8×4 frames at 24 fps, wide 180°
spread since a fireball expands radially rather than jetting in one
direction, `intensity_start: 3` for bloom) and `smoke` (alpha_blend,
`fx/smoke02.dds`, longer lifetime so it lingers and drifts upward after the
fireball fades, `enabled: true` unlike `bonfire.particles.yaml`'s disabled-
by-default smoke layer — an explosion's smoke should always show). Both
textures already exist in `data/textures/fx/`; no placeholder/missing-asset
fallback needed this time (unlike `sparks.particles.yaml`'s flat-quad
placeholder from the previous issue).

### Tests

## Output to keep in mind for next Milestone 3 issues

- **No call site triggers `VFXExplosion` yet.** This issue's scope was
  strictly the effect class itself; wiring it up is explicitly the next
  milestone item ("Wreck state: explosion + disabled vehicle," issue #831's
  own "Gates" line). Whoever implements that should also decide where the
  `explosion` `ParticleSystemTemplate` gets loaded-once-and-held (there's no
  natural per-vehicle owner the way `VehicleScrapeEffect` holds `sparks` —
  an explosion is a one-off global event, not a per-vehicle continuous
  effect — a `VFXSystem`-level cache, or a small static holder in whatever
  "wreck state" code emerges, would both work).
- `VFXExplosion::kExplosionTemplateName = "explosion"` is the asset stem to
  pass to `ParticleSystemTemplate::GetOrLoad()` — mirrors `VFXScrape::
  kSparkTemplateName`.
- The editor Play Mode / `vfx::VFXSystem` wiring gap flagged in the previous
  VFXScrape history doc still applies here too — `VFXExplosion` will
  likewise do nothing when Play-testing inside `wreckoning_editor` until
  that gap is closed.
- `physics::PhysicsSystem::SphereOverlap` is now available for any future
  "things in a radius" query (e.g. a proximity-mine trigger, an AoE ability)
  — no further physics plumbing needed.

  only documents structs/interfaces, not the query API surface consumers
  actually call.

library) — no proposal needed.

**Specification questions**: none blocking. One judgment call worth
flagging: `WRECKONING.md` mentions `VFXExplosionDesc` should "serialise
