# VFXFire

Implements GitHub issue #832: `vfx::VFXFire` — looping fire + smoke attached
to a vehicle body once damage crosses ~80% (any zone), per `WRECKONING.md`
§12 (Fire) and §6 (gameplay effects at thresholds).

## Summary of changes

### `vfx::VFXFire` (new, per issue scope)

The looping counterpart to `VFXExplosion`'s fire-and-forget shape, but
structurally closer to `VFXScrape`: `Play()`/`Update(dt)`/`IsFinished()`
satisfy the `IVFXEffect` contract so `VFXSystem` can own and reap it, but
`Update(dt)` only ticks the particle sub-systems — it never decides the
effect is done. A new `SetWorldTransform(const core::Mat4f&)` method
repositions every sub-system's emitter/renderable each frame; `Stop()` is
what actually ends it.

- `Play()` copies **every** sub-system out of `fire_template_->
  GetSubSystems()` into a member vector and builds one `ParticleEmitter`/
  `ParticleRenderable` pair per sub-system — the same "multiple layered
  sub-systems" technique `VFXExplosion` uses for fireball+smoke, needed here
  for the fire's own flame+smoke layers.
- `fire_template_` is a non-owning constructor parameter (may be `nullptr`),
  following the established `VFXScrape`/`VFXExplosion` convention: the
  caller loads it once and holds it for as long as the effect might run, so
  `core::Resource`'s delete-on-zero-refcount behaviour doesn't force a disk
  reparse every time.
- `heat_distortion` (bool, from `physics::FireDesc::heat_distortion`) is
  carried through the constructor and exposed via
  `IsHeatDistortionEnabled()`, but **not wired to any rendering pass** — see
  "Heat distortion" below.

### `vfx::VehicleFireEffect` (new) — the trigger, unlike `VFXExplosion`

Unlike `VFXExplosion` (whose issue #831 explicitly deferred the trigger to a
later issue), this issue's acceptance criteria require a concrete, working
trigger: "Driving a car past ~80% damage produces persistent smoke/fire that
follows the body." So this issue adds both the effect *and* its owner,
mirroring `VehicleScrapeEffect`:

- Implements `game::IVehicleDamageListener::OnDamageThresholdCrossed`: any
  zone crossing `desc.damage_threshold` (default 0.8) starts a `VFXFire` via
  `VFXSystem::Spawn()`; crossing the conventional last threshold (1.0, "the
  wreck threshold" — a local `kWreckThreshold` constant, since
  `VehicleDamageDesc::thresholds` doesn't name its own last entry) stops it,
  since the wreck explosion (a future issue) supersedes it.
- Implements a **new** `game::IVehicleFireListener` interface
  (`OnVehicleTransformUpdated(const core::Mat4f&)`), called once per frame
  from `GameVehicle::Update()` — this is the "follow the body" mechanism the
  issue calls for, and it didn't exist before this issue.
  `IVehicleScrapeListener` couldn't be reused: scrape is driven by discrete
  per-physics-step contact events with their own world point, but fire has
  no such event — it just needs the body's current transform every frame,
  active or not. Kept `game/`-owned and vfx-free for the same reason
  `IVehicleScrapeListener` is (`game/` must not depend on `vfx/`); wired to
  `GameVehicle` via a new non-owning `SetFireListener()` setter, mirroring
  `SetScrapeListener()`.
- **Repair-triggered stop**: the issue's acceptance criteria say the effect
  should also stop "when repaired below threshold." `IVehicleDamageListener`
  only fires on *upward* threshold crossings (`VehicleDamage::RegisterImpact`
  never decreases HP — there is no repair mechanic anywhere in the codebase
  yet, `WRECKONING.md` §8 lists it only as a planned future power-up).
  Rather than skip this criterion, `VehicleFireEffect` polls
  `damage.GetDamageFraction(zone)` for all 5 zones every
  `OnVehicleTransformUpdated()` call (already running every frame) and stops
  itself once every zone has dropped back below `desc.damage_threshold`.
  This is correct and forward-compatible once a repair mechanic lands, but
  **is currently unreachable/untestable** through the public `VehicleDamage`
  API, since damage is monotonically non-decreasing today — flagged again
  below.
- Loads the `fire` particle template once (if a `Renderer` is instanced) and
  holds it for the object's whole lifetime, for the same reason
  `VehicleScrapeEffect` holds `sparks` — a fresh `VFXFire` is constructed
  every time the fire starts, so the template must outlive many start/stop
  cycles to avoid a disk reparse each time.

### `physics::FireDesc` (new) + `GameVehicle`/`VehicleTemplate`/editor wiring

Added `FireDesc` to `physics::VehicleDesc` (mirrors `ScrapeDesc`) with
`damage_threshold` (default 0.8) and `heat_distortion` (default false).
Given full YAML round-trip + `VehicleEditorWindow` UI already exists for
every sibling `*Desc` struct (`damage`, `crash_sound`, `scrape`), added the
same for `fire` for consistency rather than leaving it editor-invisible:
`VehicleTemplate::ParseFireDesc` (runtime load), `VehicleEditorWindow`'s
load/save YAML blocks and a new `DrawFireSection()` (damage-threshold drag
float + heat-distortion checkbox). `data/vehicles/hell_sized.vehicle.yaml`
got an explicit `fire:` block for discoverability, matching how `scrape:`/
`crash_sound:` are already spelled out there even at near-default values.

`GameVehicle` gained `fire_listener_` (mirrors `scrape_listener_`) and
`SetFireListener()`; `Update()` now calls
`fire_listener_->OnVehicleTransformUpdated(transform)` right after computing
the physics body's world transform each frame, unconditionally (whether or
not a fire is currently active — the listener decides what to do with it).

`src/app/main.cpp`'s standalone vehicle spawn now constructs a
`vfx::VehicleFireEffect` alongside the existing `vehicle_scrape`, registers
it both as a `VehicleDamage` listener and as the `GameVehicle` fire
listener, and unregisters/stops it at shutdown before `VFXSystem::Shutdown()`
— same ordering concern the existing scrape-effect shutdown comment already
calls out (reaches into `VFXSystem`'s internal list via a raw pointer).

### `data/particles/fire.particles.yaml` (new)

Two looping sub-systems (`flame` additive, `smoke` alpha_blend, both
`looping: true` unlike `explosion.particles.yaml`'s one-shot burst) sized
for a vehicle body rather than a campfire: `bonfire.particles.yaml`'s flame
layer uses `size_start` 2-3/`size_end` 3-4 and `emitter_radius` 0.2; this
template scales those down (`size_start` 0.4-0.6/`size_end` 0.8-1.2,
`emitter_radius` 0.3) to stay proportionate to a ~2-4m vehicle body instead
of dwarfing it. Reuses the same textures every other fire-family template
already uses (`fx/fireflamepart01anim.dds`, `fx/smoke02.dds`) — no new art
assets needed. No embedded `lights:` entry (unlike `bonfire.particles.yaml`);
the issue only asks for particles, and a glow light can be added later
without touching this issue's scope.

### Heat distortion (per issue: "may be a stub toggle")

No screen-space post-process pass exists in the engine yet — confirmed by
searching for `PostProcess`/`distortion` across `renderer/`: the only real
post-process infrastructure is `renderer::PostProcessInfos` (exposure/bloom,
not distortion), and the only "distortion" anywhere is `WaterRenderer`'s own
self-contained forward-shader UV refraction, unrelated to a generic
screen-space pass. Per the issue's explicit "may be a stub toggle" allowance
and `WRECKONING.md`'s own wording ("optional heat-distortion post-process
**flag**", not "pass"), `heat_distortion` is a real, YAML-authorable,
editor-editable bool that flows all the way to `VFXFire::
IsHeatDistortionEnabled()` — but nothing currently reads that flag to
actually distort anything. No fake/mocked distortion effect was added.

## Output to keep in mind for next Milestone 3 issues

- **Repair-triggered stop is implemented but unreachable today.**
  `VehicleFireEffect::AllZonesBelowThreshold()` polls `VehicleDamage::
  GetDamageFraction()` every frame and is ready to stop the fire the moment
  damage drops back below threshold, but `VehicleDamage` has no public way
  to decrease HP — no repair mechanic exists anywhere yet
  (`WRECKONING.md` §8 lists "Repair (restore vehicle HP)" only as a planned
  power-up effect, `IPickupEffect::Apply(GameVehicle&)`, unimplemented).
  Whoever implements repair should add a `VehicleDamage::Repair(...)`-style
  method; `VehicleFireEffect` needs no further changes once one exists — add
  a corresponding unit test then, driving the real downward transition this
  issue could not.
- **Wreck-threshold stop is currently the only "supersession" signal.**
  `VehicleFireEffect` stops on the conventional last threshold (1.0)
  crossing, but there is still no real wreck-explosion trigger anywhere
  (issue #831's own gap). Once that trigger exists, double-check ordering:
  the fire should stop at (or just before) the moment the explosion's
  fireball starts, not noticeably before/after.
- `vfx::VFXFire::kFireTemplateName = "fire"` is the asset stem to pass to
  `ParticleSystemTemplate::GetOrLoad()` — mirrors `VFXScrape::
  kSparkTemplateName`/`VFXExplosion::kExplosionTemplateName`.
- `game::IVehicleFireListener` is a new, small, reusable "give me the body
  transform every frame" interface — any future body-attached continuous
  effect (e.g. an electrical-short spark trail from `VFXElectricity`) could
  reuse it instead of inventing another per-effect listener interface.
- No heat-distortion post-process pass exists; `physics::FireDesc::
  heat_distortion` is a real, authored, but currently inert flag. Whoever
  adds a screen-space distortion pass should read it from the active
  `VFXFire` instance(s) via `IsHeatDistortionEnabled()`.

## Propositions

**CLAUDE.md improvements** (applied, not just proposed, since they were
small additions to an already-current doc): `src/vfx/CLAUDE.md`'s module
table now lists `VFXFire`/`VehicleFireEffect`, and its "IVFXEffect contract"
section now names `VFXFire` alongside `VFXScrape` as the "externally driven,
never self-expires" exception.

**README.md**: no build/install process changes (no new third-party
library, no new CMake option) — no proposal needed.

**Specification questions**: one judgment call worth flagging —
`WRECKONING.md` §6 literally says "80% any → **smoke** particles on body"
(fire is reserved for the 100% wreck explosion), while this issue's own
title/scope explicitly asks for `VFXFire` (fire **and** smoke) at 80%. I
followed the issue over the design doc's older wording, since the issue is
the more specific, more recent source of truth and explicitly names the
class `VFXFire` with both a flame and a smoke sub-system — flag if a
reviewer wants the design doc's "smoke only" language restored instead.
