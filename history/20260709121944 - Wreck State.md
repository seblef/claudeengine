# Wreck State

Implements GitHub issue #833: the wreck state — at 100% damage, disable the
vehicle, trigger `VFXExplosion` + wreck SFX, and leave a static wreck behind.
Per `WRECKONING.md` §6 ("100% → car disabled, wreck explosion") and
Milestone 3 roadmap item 8.

## Follow-up: physics deadlock fix (found via live QA)

The initial version of this change froze the whole game the instant a
vehicle wrecked — reported by manual QA that this history doc's own
"Not done" section had flagged as unperformed. Root cause, confirmed via
debugger (a Jolt mutex shown locked at `PhysicsSystem::SphereOverlap`,
called from `VFXExplosion::ApplyShockwave`): `GameVehicle::OnCollision` is
invoked synchronously by Jolt's `ContactListener::OnContactAdded`
(`PhysicsSystem.cpp`'s `VehicleContactListener`), which fires *inside*
`jolt_system_->Update()` (`PhysicsSystem::Step()`) while Jolt holds internal
body/broadphase locks. The original `OnDamageThresholdCrossed()` called
`wreck_listener_->OnVehicleWrecked()` synchronously from that same call
stack, which reached `VFXExplosion::Play()` → `ApplyShockwave()` →
`PhysicsSystem::SphereOverlap()` — a locking Jolt narrow-phase query,
re-entering a lock already held by the same thread mid-`Step()`. Self-
deadlock. This hazard couldn't have surfaced before this issue:
`VFXExplosion` was previously only unit-tested, never actually triggered
from a live physics contact callback.

Confirmed via `GameSystem::Update()`'s frame ordering
(`for (GameObject*) obj->Update(dt)` runs *before*
`PhysicsSystem::Instance().Step(dt)` every frame) that `GameVehicle::
Update()` always runs outside any Jolt callback. Fix: `OnDamageThresholdCrossed()`
no longer calls `wreck_listener_` directly — it only flips `drive_state_` to
`kWrecked` and captures the wreck position into new `wreck_notify_pending_`/
`wreck_position_` members (neither touches Jolt). `Update()` now checks
`wreck_notify_pending_` first thing and delivers the deferred
`OnVehicleWrecked()` call there, guaranteed to run before that frame's
`Step()`. Doc comments on `GameVehicle::OnDamageThresholdCrossed()`,
`IVehicleWreckListener::OnVehicleWrecked()`, and `VehicleWreckEffect`'s
class comment all updated to state the notification is deferred by one
`Update()` tick (not "the instant" of wrecking) and explain why.

No new automated test covers this specifically — reproducing it needs a
live `PhysicsSystem`/Jolt contact callback mid-`Step()`, which
`GameVehicleTest.cpp` doesn't exist to drive (see the "no GameVehicle unit
tests" note below); this was root-caused via debugger, fixed by inspection
of the call graph, and re-verified via full rebuild + existing test suites
(no behavioural change to anything they cover — the deferred notification
is still delivered exactly once, just one frame later). Flag for the
manual QA follow-up already noted below: confirm the freeze is gone in
addition to the original explosion/SFX/control-cutoff checks.

## Summary of changes

### `game::GameVehicle` — owns the wreck transition (per issue rationale)

The issue explicitly asks for the transition to live in `GameVehicle`/
`VehicleDamage`, keeping `vfx/` a pure effects layer. `GameVehicle` now
implements `game::IVehicleDamageListener` itself and registers on its own
`damage_` in the constructor (`damage_->AddListener(this);`) — unlike
`VehicleFireEffect`, which is an *external* damage listener owned by
`main.cpp`, the wreck transition is intrinsic vehicle state, so `GameVehicle`
listens to itself.

- A new `DriveState::kWrecked` enum value joins the existing
  `kForward/kBraking/kReverse/kFlipped/kRecovering` state machine.
  `OnDamageThresholdCrossed()` transitions into it the first time `threshold`
  reaches the wreck threshold (1.0, the same `kWreckThreshold` convention
  `VehicleFireEffect.cpp` already uses for "the last configured threshold
  means wreck") — a no-op if already wrecked, so a *different* zone
  independently reaching 100% later cannot re-wreck or re-explode the
  vehicle (satisfies "a wrecked car cannot be re-wrecked or re-exploded").
- **Control cut off**: the flip-detection switch and the driver-input guard
  both gained a `kWrecked` branch — inputs are suppressed exactly like the
  existing `kFlipped` case (throttle/brake/steer/handbrake forced to zero),
  and no flip-detection/self-righting runs for a wreck (it's dead, not
  stuck).
- **Wheels freeze**: the per-frame wheel-transform loop (re-posing wheel
  meshes from the physics simulation) is skipped entirely once wrecked, so
  a wreck's wheels stop being "driven" — literally satisfying the issue's
  "stop driving wheel transforms."
- **No further damage/sound events**: `OnCollision()` now returns immediately
  when already wrecked, before forwarding to `damage_->RegisterImpact()` or
  `crash_sound_->RegisterImpact()` — an inert wreck no longer accumulates
  damage or plays crash sounds on further hits.
- Body mesh swap to a dedicated wrecked variant is explicitly out of scope
  here per the issue ("coordinated with the damage-mesh-swap issue") — not
  implemented.
- Added `IsWrecked()` (mirrors the existing `IsReversing()` accessor) since
  other systems named in `WRECKONING.md` will need to query this: the AI
  controller's `Wrecked` state (§4b) and the `WreckAll` race objective (§7).

### `game::IVehicleWreckListener` (new) — the game/vfx bridge

Mirrors `IVehicleFireListener`'s split: a `game/`-owned, vfx-free interface
(`OnVehicleWrecked(const core::Vec3f& world_position)`, called exactly once)
so a `vfx::` implementation can trigger the explosion/SFX payoff without
`vfx/` logic leaking into `game/`. `GameVehicle` gained a non-owning
`wreck_listener_` + `SetWreckListener()`, wired exactly like
`SetFireListener()`/`SetScrapeListener()`.

### `vfx::VehicleWreckEffect` (new) — the trigger

Implements `game::IVehicleWreckListener`. On `OnVehicleWrecked()`: spawns a
`vfx::VFXExplosion` (default `VFXExplosionDesc{}` — the issue didn't call for
a bespoke tuning, and `VFXExplosion` already exists fully working from a
prior issue) via `VFXSystem::Spawn()`, then triggers a one-shot wreck sound
through an owned `game::SoundEffectComponent`. Guards `triggered_` itself
too (belt-and-braces — `GameVehicle` already guarantees at most one call,
but this is the class actually responsible for not double-playing the
payoff). Loads the `explosion` particle template once via `GetOrLoad()` and
holds it for its own whole lifetime, for the same external-template-ownership
reason `VehicleFireEffect` holds `fire_template_`.

### `physics::WreckDesc` (new) + `VehicleTemplate`/editor/YAML wiring

Added `WreckDesc` to `physics::VehicleDesc` (mirrors the shape of `FireDesc`/
`ScrapeDesc`, but only needs one field): `wreck_sound` (default
`"medium-explosion"`). Unlike `CrashSoundDesc`'s placeholder-only defaults
(`"crash_light"`/etc., which have no backing asset), a real,
already-present-but-unwired asset pair (`data/sounds/medium-explosion.mp3` +
`.sound.yaml`) was found in the working tree — clearly staged in advance for
this exact feature — so `wreck_sound` defaults straight to it rather than to
a stub name. For consistency with every sibling `*Desc` (all of which have
full YAML round-trip + `VehicleEditorWindow` UI), added:
- `VehicleTemplate::ParseWreckDesc` (runtime load) alongside the other
  `Parse*Desc` helpers.
- `VehicleEditorWindow`'s load/save YAML blocks and a new
  `DrawWreckSection()` (a single sound picker, reusing the same
  `SoundEmitterSelectionModal` pattern `DrawCrashSoundSection()`/
  `DrawScrapeSection()` already use).
- `data/vehicles/hell_sized.vehicle.yaml` got an explicit `wreck:` block
  with `wreck_sound: medium-explosion`, so a wrecked vehicle actually makes
  noise during manual QA instead of silently no-op'ing.

### `src/app/main.cpp` wiring

Standalone vehicle spawn now constructs a `vfx::VehicleWreckEffect` alongside
`vehicle_scrape`/`vehicle_fire` and registers it via
`vehicle_ptr->SetWreckListener(vehicle_wreck.get())`. Unlike the fire effect,
it is **not** also added as a `VehicleDamage` listener — `GameVehicle` itself
already listens to its own damage and calls the wreck listener directly, so
`VehicleWreckEffect` only needs the one interface.

## Output to keep in mind for next Milestone 3 issues

- **Damage-mesh-swap issue**: this issue deliberately left the wrecked body
  mesh unswapped (`GameVehicle::body_mesh_` keeps its pristine template).
  Whoever implements progressive mesh swapping (`WRECKONING.md` §6's "0% →
  pristine, 30% → dented, 60% → crumpled, 100% → wrecked") should hook the
  100% case into the same `OnDamageThresholdCrossed()` wreck branch in
  `GameVehicle.cpp` — the vehicle is already guaranteed to only reach
  `kWrecked` once, so a mesh swap triggered there needs no extra guarding.
- **AI controller's `Wrecked` state** (`WRECKONING.md` §4b) and the
  **`WreckAll` race objective** (§7) can both poll the new
  `GameVehicle::IsWrecked()` accessor directly rather than re-deriving wreck
  state from `VehicleDamage` fractions themselves.
- `physics::WreckDesc` currently only carries `wreck_sound`; if a future
  issue wants a bespoke (rather than default) `VFXExplosionDesc` per vehicle
  (e.g. a bigger truck wreck shockwave), that would need a
  `vfx::VFXExplosionDesc`-shaped field added to `WreckDesc` — deliberately
  not added here since nothing in this issue's scope asked for
  per-vehicle-tunable explosion parameters, and `physics/` staying
  `vfx`-free would need `VFXExplosionDesc`'s fields duplicated as a
  Jolt-free POD rather than reused directly (same constraint `FireDesc`
  already lives with re: `VFXFire`).
- The physics body itself is **not** made static/kinematic on wreck (no
  such motion-type-mutation API is exposed anywhere in `physics/` today) —
  a wrecked vehicle can still be physically shoved around by other
  collisions, it just never drives itself again. If a future issue wants a
  literally immovable wreck, that needs a new `physics::PhysicsVehicle`/
  `PhysicsBody` API to flip motion type post-construction.
