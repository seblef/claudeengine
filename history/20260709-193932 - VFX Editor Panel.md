# VFX Editor Panel (VFXPanel)

Implements #835: an `IResourcePanel` for `.vfx.yaml` that edits `explosion` /
`electricity` / `fire` / `scrape` effect parameters with a live embedded
particle preview, per `WRECKONING.md` §14c.

## What changed

- **`editor::VFXPanel`** (`src/editor/VFXPanel.h/.cpp`): the first concrete
  `IResourcePanel` in the codebase (`ResourcesPanel`/`ResourceBrowser` framework
  existed since M1, but no panel had implemented the interface yet). Registered
  as a panel tab (`ResourcePanelRegistry::Register`, not `RegisterOpenCallback`
  — unlike `VehicleEditorWindow`, which opens in its own floating window) for
  the `.vfx.yaml` suffix, plus a `RegisterNew` skeleton-file factory.
  - Effect-type dropdown (explosion/electricity/fire/scrape) switches the
    visible parameter block; every block is always populated in `vfx::VFXDesc`
    (not just the active one) so switching types never discards previously
    authored values.
  - Parameter widgets bind directly to each effect's real descriptor struct
    (see "New vfx/ descriptors" below).
  - Optional sound picker (`SoundEmitterSelectionModal`, reused as-is from
    `VehicleEditorWindow`'s pattern) for all types except `scrape`, which
    already carries its own `screech_sound` field.
  - Save/Revert + dirty-flag tracking; `ResourceBrowser` already provides the
    unsaved-changes close modal generically via `IsDirty()`/`Save()`, so
    `VFXPanel` needed no dirty-close modal of its own.

- **Isolated preview, not the real effect classes.** `Preview` does **not**
  construct `vfx::VFXExplosion`/`VFXElectricity`/`VFXFire`/`VFXScrape`
  directly. Investigation showed each of those reaches into engine-wide
  singletons when played — `VFXExplosion::Play()` registers a real
  `game::GameLight` into whichever `GameSystem` is instanced, applies a
  physics shockwave impulse via `PhysicsSystem::SphereOverlap`, and spawns a
  `ScreenShake` that drives the *active* `ICameraController`; `VFXScrape`/
  `VFXElectricity` call `Renderer::Instance().AddRenderable()`, which enqueues
  into the same visibility system the **main editor viewport** renders from.
  In the full editor, all of these singletons *are* the live edited scene, so
  playing the real classes from an embedded preview widget would leak a real
  light flash, a physics impulse, and viewport camera shake into whatever map
  is open — confirmed with the user before proceeding (see Decisions).
  Instead, `VFXPanel` owns a self-contained preview scene modelled directly on
  `editor::ParticleEditorWindow`'s existing pattern: its own
  `particles::ParticleRenderer`, offscreen RTG, scene-infos CB, and orbit
  camera, driving raw `particles::ParticleEmitter` instances built straight
  from the effect's particle template (`explosion`/`electricity`/`fire`/
  `sparks`) — never calling `Renderer::AddRenderable()`, `GameSystem`, or
  `PhysicsSystem`. The explosion's light flash is approximated with a flat
  ImGui colour-tint overlay (alpha decaying over `light_lifetime`) instead of
  a real light. Shockwave and screen shake have no preview visual at all —
  there is nothing in an isolated preview scene for them to visibly act on.
  One-shot effects (explosion/electricity) self-stop once elapsed time passes
  their authored duration; looping effects (fire/scrape) run until the user
  clicks Stop, matching the acceptance criteria's "Stop cancels a looping
  effect." The scrape preview has no real physics contact to drive
  `UpdateContact()`, so it feeds a synthetic sinusoidal sliding-speed sweep
  into the same emission-rate/direction math `VFXScrape::UpdateContact()`
  uses, so `min_speed`/`max_speed`/`base_emission_rate` are all visibly
  exercised.

- **New `vfx/` descriptors** (scope expanded beyond the issue's stated
  dependency on `VFXExplosion` alone — see Decisions):
  - `vfx::VFXElectricityDesc` (`VFXElectricityDesc.h`) — `arc_segments`,
    `spark_rate`, `crackle_volume`, `color`, `arc_length`, `duration`.
  - `vfx::VFXElectricity` / `VFXElectricity.h/.cpp` — new concrete
    `IVFXEffect`: a one-shot arc connecting `world_pos` and
    `world_pos + direction * arc_length`, visualised as a chain of
    spark-particle bursts placed along the segment (chosen over building a
    dedicated line-rendering `Renderable`/shader — see Decisions). Follows
    the existing `VFXExplosion`/`VFXScrape` external-template-ownership
    pattern exactly (non-owning `ParticleSystemTemplate*`, tolerates
    `nullptr`). New `data/particles/electricity.particles.yaml` template
    (blue-white additive sparks) and `tests/vfx/VFXElectricityTest.cpp`
    mirroring `VFXExplosionTest.cpp`'s lifecycle-test shape.
  - `vfx::VFXFireDesc` (`VFXFireDesc.h`) — deliberately just
    `heat_distortion`; `VFXFire`'s only real authoring-time parameter beyond
    its particle template.
  - `vfx::VFXDesc` (`VFXDesc.h`) — top-level `.vfx.yaml` container:
    `effect_type` enum + all four parameter blocks + `sound`. Reuses
    `physics::ScrapeDesc` as-is for `scrape` (already exactly the
    standalone, YAML-serialisable tunables `VFXScrape`'s constructor takes;
    no `VFXScrapeDesc` duplicate was created).

- **`editor` now links `vfx`** (`src/editor/CMakeLists.txt`) — the first
  `editor → vfx` dependency; previously only `game`/`renderer`/etc.

## Decisions (raised with the user, since the issue left them open)

1. **Effect-type scope**: the issue's own "Dependencies" line only names
   `VFXExplosion` as required, but the spec (§14c) and acceptance criteria
   describe a 4-way dropdown, and only `VFXExplosionDesc` existed as a real,
   standalone descriptor beforehand (`VFXFire`/`VFXScrape` are driven by
   vehicle-nested `physics::FireDesc`/`ScrapeDesc` or ad-hoc ctor params;
   `VFXElectricity` didn't exist at all). Asked the user whether to scope the
   panel to explosion-only, ship the other 3 as disabled placeholders, or add
   real minimal descriptors for all 4 — chose the last (fullest) option.
2. **Preview isolation**: asked the user whether `Preview` should play the
   real `IVFXEffect` subclasses (fully faithful visuals, but leaks a light/
   physics impulse/camera shake into the live edited scene, as detailed
   above) or build an isolated, visual-only preview. Chose isolation; this is
   the reason the panel's preview code never touches `game::GameSystem`,
   `physics::PhysicsSystem`, or `renderer::Renderer::AddRenderable()`.
3. **`VFXElectricity`'s "arc line renderer"**: `WRECKONING.md` describes
   electricity as "arc line renderer + particle sparks". Building a real
   line-rendering `Renderable` (own shader, own draw-call hookup into the
   forward pass) is a materially larger change than a `*Desc` struct; scoped
   `VFXElectricity` to particle-only (sparks placed along the segment, no
   literal line primitive) and flagging the line-renderer visual as a
   follow-up rather than asking a third clarifying question — the particle-
   only version is still a real, tested, non-stub effect.
4. **Sound picker has no preview-playback button.** Checked
   `VehicleEditorWindow`'s crash/scrape/wreck sound sections — none of them
   wire actual audio preview playback either (`SoundEmitterSelectionModal` is
   selection-only). Matched that existing precedent instead of introducing a
   second `editor::SoundPreviewPlayer`, which would fight over OpenAL's
   single current-thread context with the one `EditorWindow` already owns.

## Output for future Milestone 3 issues

- `vfx::VFXDesc` establishes the `.vfx.yaml` top-level schema
  (`effect_type` + per-type block + `sound`) — any future `IVFXEffect`
  subclass added to the engine should get a matching `*Desc` struct and a
  new `VFXEffectType` enumerator plus panel branch, following this file's
  pattern.
- The isolated-preview pattern (own `ParticleRenderer`/RTG/camera, raw
  `ParticleEmitter`s, no `Renderer::AddRenderable()`/`GameSystem`/
  `PhysicsSystem`) is now precedented twice (`ParticleEditorWindow`,
  `VFXPanel`) — any future panel needing a live particle preview should copy
  this rather than reaching for `renderer::PreviewRenderer` (which only
  renders `MeshInstance`+`GlobalLight`, no particle support at all).
- Follow-up candidates, in rough priority order: (1) exercise
  `VFXElectricity`/`VFXFire`/`VFXScrape` panel round-trips visually once a
  graphical session is available; (2) consider a real arc line-rendering
  primitive for `VFXElectricity` if the particle-only look isn't convincing
  in practice; (3) if a future issue needs in-panel audio preview, wire it
  through `EditorWindow`'s existing shared `SoundPreviewPlayer`/OpenAL
  context rather than creating a second one.

## CLAUDE.md / instruction sections specifically applied

- Root `CLAUDE.md` — "Verification": no windowed binary launched; relied on
  `cpplint`/`cppcheck`/full rebuild/`ctest`, and flagged the live-preview QA
  gap explicitly above instead of claiming untested success.
- `src/vfx/CLAUDE.md` — "External template ownership": `VFXElectricity`
  takes its particle template as a non-owning constructor parameter and
  tolerates `nullptr`, exactly like `VFXExplosion`/`VFXScrape`.
  "Graceful degradation with no singletons instanced" shaped
  `VFXElectricity`'s `Renderer::IsInstanced()` guards and the accompanying
  unit tests (lifecycle with nothing instanced, mirroring
  `VFXExplosionTest.cpp`'s coverage shape).
- `src/editor/CLAUDE.md` — "GUI vs. edition logic separation": `VFXPanel` is
  pure UI plus its own isolated preview simulation; no gameplay/physics/audio
  side effects reach the live edited scene. "Prefer `std::find_if`/STL
  algorithms over raw loops" — used `std::transform` for building
  `preview_emitters_` from `preview_descs_`, matching
  `ParticleEditorWindow::RebuildPreview()`.
- `src/CLAUDE.md` — one class per `.h`/`.cpp` pair; new modules'
  `CMakeLists.txt` updated (`vfx`, `editor`, `tests/vfx`).
